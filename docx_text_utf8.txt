1. Mục tiêu và phạm vi
Tài liệu này mô tả đầy đủ API cho các nhóm chức năng nội dung trọng tâm:
Danh mục nội dung cho “Truyền thống bộ đội” và “Nét tiêu biểu” gồm 2 cấp: (1) Cấp đề mục (root) và (2) Cấp nội dung (leaf/child).
Mọi đối tượng có CRUD, ẩn/hiện (visibility), và thứ tự hiển thị (sort order).
Ca khúc truyền thống có phân loại theo danh mục và có CRUD, ẩn/hiện, thứ tự tương tự.
Chuẩn hóa response, phân quyền, soft delete, phân trang, tìm kiếm, sắp xếp.
Tài liệu thực thi (Execution doc) ở cuối dùng để triển khai theo từng bước: thiết kế DB, API, kiểm thử, và triển khai.
2. Giả định & thuật ngữ
API theo chuẩn REST, trả về JSON.
Xác thực bằng JWT Bearer token (hoặc tương đương).
Soft delete: xóa logic (deleted_at) để tránh mất dữ liệu.
Ẩn/hiện: is_visible (true/false). Với End-user chỉ thấy dữ liệu is_visible=true và không bị xóa.
Thứ tự: sort_order (integer). Số nhỏ hiển thị trước.
Ký hiệu:
Admin API: dành cho quản trị (có quyền).
Public API: dành cho người dùng cuối (End-user).
3. Tổng quan module theo Master plan
Theo file Master plan, các module liên quan trực tiếp gồm: “Truyền thống bộ đội/Nét tiêu biểu”, “Quản lí nội dung bài viết”, “Ca khúc truyền thống”, “Quản lý ca khúc”.
Tài liệu này tập trung đặc tả phần danh mục + nội dung + ca khúc; các module khác (ghi chú, hồ sơ, báo cáo...) sẽ tách tài liệu nếu cần.

5. Chuẩn API (Request/Response)
5.1. Header & Auth
Header: Authorization: Bearer <token>
Content-Type: application/json (trừ endpoint upload dùng multipart/form-data)
Timezone: server lưu UTC; client hiển thị theo locale.
5.2. Chuẩn response
Response thành công (gợi ý):
{ "success": true, "data": <object|array>, "meta": { ... } }
Response lỗi (gợi ý):
{ "success": false, "error": { "code": "VALIDATION_ERROR", "message": "...", "details": [ ... ] } }
5.3. Phân trang, tìm kiếm, sắp xếp
Pagination: ?page=1&page_size=20 (tối đa 100)
Search: ?q=keyword (search theo name/title/summary)
Sort: ?sort=sort_order&order=asc | ?sort=created_at&order=desc
Filter: ?is_visible=true/false (chỉ admin được filter false)

10. Quy tắc nghiệp vụ quan trọng
10.1. Danh mục 2 cấp
Cấp đề mục: parent_id = NULL.
Cấp nội dung: parent_id != NULL; chỉ cho phép tối đa 2 cấp (không cho phép child của child).
Nội dung bài viết chỉ được gắn vào danh mục cấp nội dung (child).
10.2. Ẩn/hiện
Ẩn danh mục: end-user không thấy danh mục đó; tùy nghiệp vụ có thể ẩn luôn toàn bộ child và content bên dưới (khuyến nghị: ẩn theo cây).
Ẩn nội dung/ca khúc: end-user không thấy item đó.
Admin luôn có thể xem tất cả (kể cả is_visible=false) qua admin endpoints.
10.3. Thứ tự hiển thị
sort_order là số nguyên >= 0.
Khi reorder: gửi mảng orders gồm (id, sort_order). Server validate tất cả id thuộc cùng scope (cùng parent_id/type hoặc cùng category_id).
Khuyến nghị: khi tạo mới mà không có sort_order thì tự gán = max(sort_order)+1 trong scope.
10.4. Ràng buộc khi xóa
Xóa danh mục cấp đề mục: 
Có thông báo xóa toàn bộ nội dung
Xóa danh mục cấp nội dung: 
Có thông báo xóa toàn bộ nội dung
Xóa media: cân nhắc chặn nếu media đang được tham chiếu (cover/audio).

12. Tài liệu thực thi (Execution Document)
12.1. Deliverables
Thiết kế DB (migration + seed data mẫu).
Implement API endpoints (Admin + Public).
Tài liệu API (Swagger/OpenAPI).
Test plan + test cases (API + UI tích hợp nếu có).
Deploy checklist + monitoring.
12.2. Kế hoạch triển khai theo bước (khuyến nghị)
Bước 1 - Chốt mô hình dữ liệu: xác nhận 2 cấp danh mục cho nội dung và có/không 2 cấp cho danh mục ca khúc.
Bước 2 - Migration DB: tạo bảng content_categories, content_items, song_categories, songs, media_assets; thêm index theo (type,parent_id,sort_order), (category_id,sort_order), (is_visible).
Bước 3 - Seed: tạo sẵn danh mục root cho TRUYEN_THONG và NET_TIEU_BIEU (nếu cần) và 1-2 danh mục con mẫu.
Bước 4 - Implement Media upload: lưu storage (local/MinIO/S3), trả về url.
Bước 5 - Implement Admin APIs: CRUD + visibility + reorder cho categories/items/songs.
Bước 6 - Implement Public APIs: list/detail cho categories/items/songs; áp filter is_visible=true + sort_order asc.
Bước 7 - Validation & business rules: giới hạn 2 cấp, ràng buộc xóa, ràng buộc audio_url xor audio_media_id.
Bước 8 - Logging/Audit (tuỳ chọn): ghi lại ai tạo/sửa/xóa, lịch sử publish.
Bước 9 - Testing: unit test service + integration test API; kiểm thử phân quyền.
Bước 10 - Deploy: migration chạy an toàn, cấu hình storage, cấu hình CORS, backup DB, giám sát lỗi.
12.3. Checklist kiểm thử (tóm tắt)
Danh mục: tạo root/child đúng rule 2 cấp; không cho phép tạo cấp 3.
Danh mục: reorder đúng scope; sort_order trùng vẫn hiển thị ổn (server nên normalize nếu cần).
Danh mục: ẩn root -> public không thấy (và không thấy child).
Nội dung: chỉ gắn vào category child; public chỉ thấy item is_visible=true.
Ca khúc: upload audio, play/pause ở FE (API cung cấp url); lyric hiển thị đúng.
Xóa: soft delete; public không truy cập được; admin có thể lọc deleted nếu cần.
Security: role không đủ quyền bị 403; token invalid bị 401.
12.4. Gợi ý cấu trúc OpenAPI/Swagger
Mỗi endpoint cần mô tả: request schema, response schema, mã lỗi, và ví dụ payload. Có thể sinh tự động từ code (NestJS/Express/Spring/.NET) tuỳ stack.
